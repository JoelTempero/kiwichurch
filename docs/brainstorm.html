Kiwi Church Community Platform

Brainstorm & Design Review - 17 April 2026

TL;DR The existing portal already covers ~70% of the client's requirements. We don't need to start from scratch. The recommended approach is to modernise the existing codebase (migrate to Tailwind v4, add react-hook-form + zod) and build the missing features on top (real-time chat, global search, push notifications, polls, moderation). This saves months of work and keeps everything Joel's already built.

3. Approaches

A. Full Rebuild from Scratch

Throw away the existing code. Scaffold a new Vite + React + TS + Tailwind v4 project. Rebuild everything following the CMS-Portal-Backend playbook from Phase 1.

PROS
  • Clean architecture from day one
  • Tailwind v4, react-hook-form + zod, cn() utility from the start
  • Modern folder structure matching playbook exactly
  • No legacy CSS to untangle
CONS
  • Wastes months of existing work (~12 pages, ~27 components, full service layer)
  • The Firebase backend (rules, collections, types) doesn't change either way
  • Significantly more expensive in time and tokens
  • Violates Joel's core principle: "edit, don't rewrite"

B. Modernise + Extend (Evolve the Existing Codebase)

Keep the existing app. Migrate styling from vanilla CSS to Tailwind v4. Add react-hook-form + zod for forms. Then build the missing features (chat, search, notifications, polls, moderation) on top of what's already working.

PROS
  • Preserves all working features — events, groups, kete, auth, directory, admin
  • Firebase backend (rules, types, services) stays as-is
  • Faster to ship v1 — only building what's actually missing
  • Incremental and deployable at every step
  • Lower token cost and less risk of regressions
CONS
  • CSS migration is tedious (59KB of vanilla CSS to convert)
  • Existing code may need some refactoring to accommodate new features
  • Won't perfectly match the playbook folder structure

C. Hybrid: New Shell, Port Features

Scaffold a new Tailwind v4 project shell (layout, routing, auth). Then port existing feature logic (services, hooks, types, stores) directly — they're well-structured and mostly framework-agnostic. Rebuild only the UI components in Tailwind.

PROS
  • Clean Tailwind foundation without CSS migration headaches
  • Preserves the valuable backend layer (services, hooks, types, stores)
  • Fresh UI that matches our current design standards
  • Structured like a rebuild, priced like a migration
CONS
  • More work than Approach B (rebuilding all UI components)
  • Risk of subtle regressions in ported logic
  • Porting is tedious — lots of copy-paste-adapt
Recommendation: Approach B (Modernise + Extend) The existing codebase is solid. The service layer, hooks, types, and stores are well-architected. The only real weakness is the vanilla CSS. A Tailwind migration is tedious but straightforward, and it's far less work than rebuilding 27 components and 12 pages from scratch. The new features (chat, search, notifications) are independent enough to bolt on cleanly.

4. Key Design Decisions (For Joel)

1. Real-time chat: Firestore or Firebase Realtime Database?

Recommendation: Firestore for messages, RTDB for presence/typing indicators only.

Firestore gives us better querying (search messages by date, user, content), offline persistence, and security rules we already know. RTDB is better for ephemeral real-time state like "Joel is typing..." and online/offline presence. This hybrid approach is what Firebase themselves recommend.

Cost consideration: Firestore charges per read. A busy group chat could generate lots of reads. Mitigations: paginate message history (load last 50, scroll to load more), use onSnapshot for live updates (only charges for new/changed docs), and set up Firestore bundle caching for frequently accessed channels.

2. 1:1 messaging: How to model it?

Recommendation: A conversations collection with a sorted participant pair as the document ID (e.g., uid1_uid2 where uid1 < uid2). Messages as a subcollection. This makes it easy to look up "does a conversation between these two users exist?" and avoids duplicates.

Each user gets a conversationMeta subcollection on their user doc for inbox display (last message preview, unread count, timestamp) — denormalised for fast list rendering.

3. Push notifications: What's the plan?

Recommendation: Firebase Cloud Messaging (FCM) via a Cloud Function triggered on new messages/events/announcements. The PWA already supports service workers, so adding push notification support is a natural extension.

Requires: a Cloud Function to send notifications, FCM token management (store per-user device tokens in Firestore), and user permission prompts in the app.

Desktop notifications: Use the Web Notification API alongside FCM for when the app is open in a browser tab.

4. Global search: Client-side or server-side?

Recommendation: Client-side for v1 with a path to Algolia/Typesense later if needed.

For a community of likely <500 members, client-side search across users and recent messages is fast enough. Use Firestore's where + orderBy for basic text matching, and TanStack Query's client-side filtering for loaded data. If the community grows significantly, add Algolia (Firebase has a native Algolia extension).

5. E2E encryption and 2FA?

Recommendation: Defer both to post-launch.

E2E encryption is a massive engineering effort (key management, key rotation, multi-device sync) that's overkill for a church community app. Firestore security rules + HTTPS + Firebase Auth already provide strong security. If the client specifically asks, we can add it for private channels later using the Web Crypto API.

2FA via Firebase Auth is straightforward to add later but adds friction for a community app. Recommend making it optional and admin-configurable post-launch.

6. CSS migration strategy?

Recommendation: Incremental migration. Install Tailwind v4 alongside the existing CSS. New components and pages use Tailwind from the start. Existing components get migrated page-by-page as we touch them. Delete old CSS rules as they're replaced.

This avoids a "big bang" migration that could break everything, and means every commit is deployable.

7. What about the static HTML pages in the root?

Recommendation: Keep them for now, plan to replace. The client mentions "shift current website connection over to the new one" in their rollout plan. The static HTML pages (about.html, calendar.html, etc.) are the current public website. Eventually the portal becomes the primary destination, but that's a later phase. For now, don't touch them.

5. Subsystem Decomposition

This project is too large for a single spec. Here are the independent subsystems, in recommended build order:

Phase 1: Foundation Modernisation

  • Install Tailwind v4 alongside existing CSS
  • Add react-hook-form + zod
  • Add cn() utility (clsx + tailwind-merge)
  • Migrate layout components to Tailwind first
  • Add Lucide React icons
  • Verify all existing features still work
Effort: Medium ~2-3 sessions

Phase 2: Real-Time Group Chat

  • Upgrade group message boards to real-time chat UX
  • Chat input with file attachments
  • Message reactions (emoji picker)
  • @mentions with autocomplete
  • Threaded replies
  • Typing indicators (RTDB)
  • Unread message counts
Effort: Large ~4-6 sessions

Phase 3: Direct Messaging

  • Conversations collection + data model
  • DM inbox with conversation list
  • 1:1 chat view (reuse group chat components)
  • Start conversation from directory/profile
  • Unread counts in navigation
Effort: Medium ~2-3 sessions

Phase 4: Notifications System

  • Cloud Function for FCM push notifications
  • FCM token management per device
  • Web Notification API for desktop
  • Notification preferences (per-channel muting)
  • Priority alerts for @mentions
  • Complete the existing NotificationPanel UI
Effort: Medium ~2-3 sessions

Phase 5: Global Search

  • Complete the existing SearchPanel component
  • Search across: messages, users, files, events, kete
  • Filters: date range, user, channel/group, content type
  • Search result previews with navigation
  • Recent searches
Effort: Medium ~1-2 sessions

Phase 6: Polls & Engagement

  • Poll creation within groups
  • Single/multi-choice, anonymous option
  • Real-time vote counts
  • Announcements (admin broadcast to all/specific groups)
  • Discussion forums (structured threads vs chat)
Effort: Medium ~1-2 sessions

Phase 7: Moderation & Admin

  • Content reporting and flagging
  • Moderation queue for reported content
  • Message edit/delete for moderators
  • Audit log (all admin actions)
  • User suspension capability
  • Add moderator role to existing role system
Effort: Medium ~2-3 sessions

Phase 8: Polish & Launch Prep

  • Complete Tailwind migration for remaining pages
  • Mobile responsiveness audit
  • Accessibility audit (WCAG 2.1 AA)
  • Security audit (Firestore rules, storage rules)
  • Performance optimisation
  • Client testing invite (prototype phase)
Effort: Medium ~2-3 sessions
Total estimated effort: ~16-25 sessions

This is a significant project. The client's rollout plan (prototype → invite groups → go live) aligns well with incremental delivery. We can ship after Phase 4 (chat + DMs + notifications) for the prototype testing phase, then layer on search, polls, and moderation before going fully live.

6. Proposed Data Model (New Collections)

These are the new Firestore collections needed alongside the existing ones:

conversations (1:1 direct messages) 
conversations/{conversationId}
  participants: string[]          // [uid1, uid2] sorted
  participantNames: Record<string, string>
  lastMessage: {
    content: string
    senderId: string
    timestamp: Timestamp
  }
  createdAt: Timestamp
  updatedAt: Timestamp

  messages/{messageId}
    senderId: string
    senderName: string
    senderPhotoURL: string
    content: string
    attachmentURL?: string
    attachmentType?: 'image' | 'document' | 'video'
    readBy: Record<string, Timestamp>
    createdAt: Timestamp
    editedAt?: Timestamp
chatMessages (group channel messages - upgrade of existing board posts) 
gatherings/{gatheringId}/messages/{messageId}
  senderId: string
  senderName: string
  senderPhotoURL: string
  content: string
  attachmentURL?: string
  attachmentType?: 'image' | 'document' | 'video'
  threadId?: string              // parent message ID for threads
  threadCount?: number           // reply count (denormalised on parent)
  reactions: Record<string, string[]>  // emoji -> [userIds]
  mentions: string[]             // mentioned user IDs
  pinned: boolean
  edited: boolean
  editedAt?: Timestamp
  createdAt: Timestamp
polls 
gatherings/{gatheringId}/polls/{pollId}
  question: string
  options: { id: string, text: string }[]
  multiSelect: boolean
  anonymous: boolean
  closesAt?: Timestamp
  createdBy: string
  createdAt: Timestamp

  votes/{oderId}
    optionIds: string[]
    createdAt: Timestamp
reports (moderation) 
reports/{reportId}
  reporterId: string
  targetType: 'message' | 'post' | 'comment' | 'user'
  targetId: string
  targetCollectionPath: string   // full path to the reported document
  reason: string
  status: 'pending' | 'reviewed' | 'actioned' | 'dismissed'
  reviewedBy?: string
  reviewedAt?: Timestamp
  action?: 'deleted' | 'warned' | 'suspended' | 'none'
  createdAt: Timestamp
auditLog 
auditLog/{logId}
  action: 'create' | 'update' | 'delete' | 'suspend' | 'unsuspend' | 'role_change' | 'moderate'
  actorId: string
  actorName: string
  targetType: string
  targetId: string
  description: string
  metadata?: Record<string, any>
  createdAt: Timestamp
presence (Firebase Realtime Database, not Firestore) 
/presence/{userId}
  online: boolean
  lastSeen: number (timestamp)
  typing?: {
    channelId: string
    timestamp: number
  }
