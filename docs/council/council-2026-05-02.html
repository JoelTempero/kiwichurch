🛡️ The Sentinel Security Hardliner
Storage delete rules grant any authenticated user the ability to delete all uploaded media. getAllUsers() contradicts security rules and will fail for members. No App Check means the API is callable without loading the website. The platform has doors that look closed but aren't latched.

This project has a pattern I see constantly in Firebase apps: the rules look thorough on first read, but the authorization model is full of semantic gaps. The contactMessages collection allows create: if true with no constraints on document shape, size, or frequency. Any script can flood that collection with garbage. No Cloud Functions exist to throttle it. No captcha protects it.

The Storage rules are worse than they appear. Every single path under /kete/, /events/, /gatherings/, and /resources/ grants allow delete: if isAuthenticated(). That means any member who signs up (registration is open and instant) can delete every uploaded image and document belonging to other users. One disgruntled member and your media library is gone.

The users collection read rule (request.auth.uid == userId || isAdmin()) contradicts the application code. getAllUsers() is called from DirectMessagesPage, SearchPanel, and DirectoryPage for regular members. This query will fail for non-admin users. Either the app is already broken for members, or the Firestore emulators are hiding the permission failures during dev.

The deactivated status enforcement is entirely absent from security rules. A deactivated user retains their Firebase Auth credentials, can sign in, and has full member-level access to every collection. The username enumeration leak is similarly still present. The Firebase API key absence of App Check means any HTTP client can call your Firestore and Auth APIs directly.

🧬 First Principles Thinker Problem Reframer
The audit asks "what bugs need fixing" but the actual question is "can 30 church members use this next Sunday?" Half the 18 items are irrelevant to that goal. The architecture is fine for a church. The product readiness is not. Focus on: auth resilience, registration decision, fresh events, deactivation enforcement.

What if the bug list is solving the wrong problem? The audit categorizes by technical severity. But severity for whom? A deprecated persistence API and an O(n) membership query are engineering debt. They will not prevent anyone from joining a group next week. Meanwhile, "Darryl cannot log in" and "anyone can create an account with no approval" are the only two items that will generate a confused phone call from a real person.

You have 5 registered users. The system has 16 pages, 28 components, polls, emoji reactions, moderation queues. How many of those features will be used in the first month? Groups, events, maybe the blog. The moderation queue will sit empty because there is nothing to moderate when your community is 30 people who see each other on Sunday.

The auth flow is the wall. The system was built for a user who already exists in both Firebase Auth AND Firestore. The moment those two get out of sync, the app silently treats you as logged out. For a non-technical church administrator, this is indistinguishable from "the app is broken." The fix is: what happens when getUser(uid) returns null for a valid auth session? The answer should never be "pretend they are not logged in."

Here is what I would strip the fixlist down to for "usable next Sunday": (1) Auth resilience when Firestore user doc is missing or slow. (2) A decision on open vs. gated registration. (3) Fresh event data so the homepage is not empty. (4) The deactivated-user enforcement. Everything else addresses scale problems at 30 users with no evidence they matter yet.

🔨 The Hammer Bot Buster
5 attack vectors: contact form spam (unlimited, unauthenticated), username enumeration (public reads + distinct errors), notification flood (any auth user, no volume cap), bot farm via open registration, and public Firestore reads as a billing attack. None require sophistication.

Vector 1: Contact form spam. The contactMessages rule is allow create: if true. No authentication. No CAPTCHA. No honeypot. No document size limit. I write a 12-line loop that posts garbage until your bill spikes or admin inbox is buried.

Vector 2: Username enumeration. The usernames collection has allow read: if true. Dictionary attack against this endpoint. Login flow compounds: username not found vs wrong password gives two distinct oracles.

Vector 3: Notification spam. Any authenticated user can write unlimited notifications to any other user. No volume limit, no deduplication, no cooldown. One batch write, 500 notifications.

Vector 4: Open registration as bot farm. No CAPTCHA on signup. No email verification gate. I script 1,000 accounts in an hour. Each can post, send DMs, create reports, and spam notifications.

Vector 5: Public reads billing. Kete, settings, and usernames collections all allow read: if true. A bot issues reads continuously. You pay per read. No caching layer between the internet and your billing meter.

🐒 The Chaos Monkey Failure Injector
Total trust in Firebase availability with zero verification that it's actually responding. Every subscription silently drops on connection loss, auth treats a timeout identically to "not logged in," and the service worker's Firestore caching guards a door nobody walks through (SDK uses WebChannel, not fetch).

Your user is in a group chat. Firebase hiccups. All four onSnapshot subscriptions pass a callback for success and nothing for error. The Firestore SDK swallows the disconnection, the listener goes dormant, and the UI freezes on stale data. The user keeps typing, hits send, the writeBatch queues locally. When it comes back, maybe the batch applies. The user will never know.

The auth flow: Zustand hydrates from localStorage. Then onAuthStateChanged fires, calls getUser(uid), and if Firestore is unreachable, that promise hangs. No timeout. No error catch. The user stares at a spinner forever. Or worse: if the SDK returns from cache, the user gets a potentially stale role assignment.

The service worker's NetworkFirst rule for firestore.googleapis.com will only catch REST-based reads (which this app does not make). The Firestore SDK uses WebChannel transport. The service worker is guarding a door nobody walks through.

Single-provider monoculture: Auth, database, storage, hosting, real-time subscriptions all Firebase, one project. A regional outage takes everything simultaneously. No health check, no navigator.onLine listener, no connection state subscription. The app assumes Firebase is there and behaves as though network failures are impossible.

🐌 The Slow Drip Resource Exhaustion Specialist
A patient attacker operating below detection can inflict $15-200/month via contactMessages spam (1MB docs at 45-second intervals), Storage uploads (10MB files, no lifecycle policy), and notification writes that trigger onSnapshot reads on recipients. No single request is anomalous. You notice on the monthly invoice.

contactMessages: allow create: if true. No auth, no captcha, no rate limit, no field validation. One request every 45 seconds. Each document 900KB. 1,920 documents per day. 57,600 in 30 days. ~51GB stored data. Storage cost accumulates to $9/month and grows every month.

Authenticated path: registration is open. I upload 10MB images to kete/{randomId}/ at one per hour across 5 accounts. 6GB/day. 180GB in 30 days. $4.68/month storage growing perpetually. No lifecycle policy, no Cloud Function to garbage-collect orphaned uploads.

Conversations: one message per minute across all real users. Two writes per message. Each triggers onSnapshot reads on the recipient. Your Firestore read bill grows proportional to (write rate * active users).

30-day total: $15-200 depending on Storage aggression and active listener count. None triggers alerting. Firebase has no built-in anomaly detection for slow accumulation.
